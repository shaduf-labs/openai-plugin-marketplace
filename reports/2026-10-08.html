Before replacing an onboarding GPT link: establish teammate continuity

Enterprise creator-to-teammate · ChatGPT web / Chat · four primary sources · migration/use NOT RUN. Research-call clock bracket: 13:01:50–13:03:01 UTC. An inspection window, not individual HTTP timestamps or a release/change date.

Change the controlled entry point last—not as proof that conversion worked. Preserve real work, establish replacement access, check the intended teammate’s installation/selection and compare useful familiar output.

Use the five-step onboarding-link decision and stop/fork →

The illustrative situation—and the decision

A creator has a published instructions/reference team-writing GPT in an affected Enterprise workspace. Intended teammates draft from supplied text with that creator’s real team-style reference and required format in ChatGPT web / Chat, reached through one creator-controlled onboarding document. This is not a supplied account, customer, task, reference, prompt/output or observed migration. Published does not necessarily mean publicly shared.

Four separate boundaries matter: preserved real work → replacement shared/permitted → intended recipient installed/selected → useful familiar output. Conversion alone establishes none of the last three. Our ordering of the controlled-document handoff is synthesis, not an official automatic old-GPT-URL redirect. Migration · creator Steps 1–4; Build plugins · testing / sharing.

What changes the next action

  • Preserve before conversion: actual audience, instructions/files/template, useful prompts and good results, including a harder case; finish important edits. The original becomes read-only but is documented usable until retirement. This is a state distinction, not this workspace’s retirement date.
  • Access and maintenance have owners: private replacement, direct Share plugins, Publish plugins to workspace and universal public listing differ. Use plugins, sharing, Available/Installed policy and web creator/editor prerequisites differ too. Ask the admin if blocked; naming a maintainer does not grant editing.
  • Test the recipient route: intended destination, details/plus installation unless admin-installed, new ChatGPT chat and explicit @ plugin/skill selection. Creator access is not recipient evidence.
  • Compare the real outcome: same text/prompt/reference, saved good result, harder case and normal request. Check facts/style/format/reference use/completeness/time, not assumed model/tools/context equivalence. After adequate evidence, update the controlled destination plus install/select guidance, genuine prompt, maintainer and differences; review preserved/changed files and repeat saved tests after edits.

Missing required access/capability? Hold switching that workflow. An ordinary prompt, reusable skill/project, existing authorized integration or purpose-built solution may suffice; none is a tested drop-in here. Reference-only work needs no app connection. Actual integration dependencies/custom actions and outside audiences need separate verified scope, not an invented MCP rebuild. Migration · Switch after the workflow is ready; Plugin controls · capability chain.
