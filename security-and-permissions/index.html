Security and permissions

Write down who supplies the data, who can authorize access and which actions must stop for confirmation. Installing a package does not erase any of those boundaries.

This is our engineering worksheet, not a platform form.

Review does not establish that every deployment is safe. The worksheet applies the saved security guidance to a task; it is not a tested threat model, an OAuth implementation recipe or a new mandatory submission requirement.

Text alternative: data enters the task boundary; host/workspace controls and server authorization constrain tool access; actions retain consent requirements. Neither source instructions nor accurate metadata authorize an operation.

MCP server, Security & Privacy. Checked 29 Sep 2026.

Identity ≠ resource access ≠ feature entitlement

Narrow boundary checked 3 October 2026. The MCP server must verify credentials/required scopes and enforce permissions; declaring authentication or showing UI is not enforcement. An authenticated account may still lack access to a project, and authorized project access does not establish a paid feature entitlement. Authentication · Implementing token verification, Security & Privacy · Authentication & authorization / Data handling, B12/B13.

Our proposed sequence is identity → requested resource → actual feature entitlement → included read or truthful denial. Missing/expired authentication and denied resource access are not upgrade opportunities; unknown entitlement is not “upgrade required.” Only offer a fallback if genuinely included and authorized. Exact ordering/copy is our design synthesis / NOT RUN, not an OAuth recipe, observed enforcement result or approval. Use the concrete linkless denial and six hypothetical cases. The 1 October release-rehearsal kit safely checks selected source/archive paths and byte parity under its stated policy. Allowlisting is packaging engineering, not a secret scanner or proof of model safety.

  • H04: requested email, draft only. No claimed outside action; other enabled tools retain their own authorization boundary—NOT RUN.

Complete a data and permission worksheet

Data provenance
List each supplied/retrieved input, its owner and its sensitivity. Which passages are evidence rather than instructions?
Least privilege
Name the minimum resources and read/write scopes. Remove access unrelated to the first task; document what the user cannot authorize.
Identity and authorization
Which provider account, organization or service identity performs the operation? What happens when access is denied or expired? Do not place credentials in the package.
Minimization and retention
Which data must leave the host? What is stored, for how long and by whom? Specify deletion/retention and redact diagnostic/reviewer logs.
Injection boundary
How will a tool result or transcript asking to send/disclose data be treated? Test that source content cannot enlarge the user’s task.
Action consent
For each write, send, purchase or irreversible action, record what the user sees and confirms. Separate draft preparation from execution.
Evidence and revocation
What can the user inspect after the call? Which plugin, service/MCP and operating-system permissions must be removed separately?

Describe tools and UI honestly

Public MCP review uses explicit read/write, destructive and open-world annotations. They must match actual behavior; do not mark a mutating operation as harmless for convenience. Annotation-justification documentation is conflicting—keep that unresolved portal check in the submission plan.

MCP review and distribution, Submission error reference. Checked 29 Sep 2026.

If a UI is useful, preserve the iframe/CSP boundary and separate its display role from server authorization and input validation. An interactive result does not by itself prove a safe service action. We have not implemented or threat-tested a connected version of Meeting Evidence.

Before allowing a connection

  • Identify intended user/provider/workspace permission—not only a directory listing.
  • Review included workflow resources and requested capabilities; keep secrets/private data out of distributable files.
  • Start with a bounded read or unsent draft and a source-to-output inspection.
  • Test injected/missing input and denied access; record observed behavior rather than claiming safety from review.
  • Document separate disable/uninstall and access-revocation steps.
